## 1. 사전 기술 검증 결과 (2026-11-08)

로컬에서 브이월드가 연결되지 않았던 원인은 **브이월드 API가 CORS 헤더를 보내지 않아 브라우저가 응답을 차단**하기 때문일 가능성이 큽니다. 브이월드는 `callback=` 파라미터를 주면 JSONP로 응답하므로, 정적 사이트에서도 일부 API는 직접 호출할 수 있습니다.

| 데이터 | 브라우저 직접 호출 | 방식 | 비고 |
|---|---|---|---|
| 브이월드 2D 데이터 API (`/req/data`) | ⭕ | JSONP | CORS 없음, JSONP 응답 확인 |
| 브이월드 검색 (`/req/search`)·주소 (`/req/address`) | ⭕ | JSONP | 위와 동일 서버 |
| 브이월드 지도 타일 (WMTS) | ⭕ | 이미지 | CORS 불필요 |
| 브이월드 부동산 속성 API (NED: 토지이용계획·공시지가 등) | ⭕ (2026-11-09 정정) | JSONP | 무효 키일 때만 JSONP가 아닌 오류를 돌려줘 막힌 것처럼 보였음. 유효한 키로는 JSONP 정상 |
| 브이월드 WFS | ❌ | 중계 필요 | CORS 없음 |
| SGIS (통계청 인구·가구·사업체) | ⭕ | fetch | `Access-Control-Allow-Origin: *` |
| 공공데이터포털 (`apis.data.go.kr`: 건축물대장·기상청 등) | ⭕ | fetch | 요청 출처를 허용하는 CORS 헤더 확인 |
| 카카오 로컬 (주변 시설) | ⭕ | fetch | CORS 허용 |
| 서울 열린데이터 | ❌ | 중계 필요 | http 전용 → https 사이트에서 차단 (현재 우선순위 낮음) |

> ⚠️ 위 표는 **유효하지 않은 테스트 키**로 응답 헤더만 확인한 결과입니다.
>
> ✅ **2026-11-08 실제 키 검증 (Phase 0):** 배포 주소(https://cjg10040.github.io/site-agent/)에서 브이월드 지도 타일·장소 검색·주소→좌표·2D 데이터(연속지적도) 네 항목이 모두 정상 응답. 정적 사이트 + JSONP 구조로 브이월드 직접 호출이 가능함을 확인.

## 2. 시스템 구성

```text
┌─────────────────────────── 사용자 브라우저 ───────────────────────────┐
│  GitHub Pages 정적 앱  (https://<계정명>.github.io/<저장소명>/)          │
│                                                                        │
│   설정 화면 ── API 키 입력 → 브라우저에만 저장(localStorage)             │
│   프로젝트 ── IndexedDB (대지·카드·사진) ⇄ 프로젝트 파일(.zip) 내보내기  │
│                                                                        │
│   ├─ 직접 호출 ──▶ 브이월드(JSONP·타일) / SGIS / 공공데이터포털 / 카카오  │
│   └─ 중계 호출 ──▶ Cloudflare Worker ──▶ 브이월드 NED·WFS 등            │
│                                                                        │
│   프롬프트 생성 ──(복사)──▶  [외부 챗봇: ChatGPT·Claude·Gemini 등]       │
│   카드 보드 ◀──(답변 붙여넣기 → 파서)──┘                                 │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.1 중계 서버(Cloudflare Worker) 원칙 — 현재 불필요 (참고용으로 남김)

- 2026-11-09 기준 사용하는 API(브이월드 전체, SGIS, 건축HUB)가 모두 브라우저에서 직접 호출되어 중계 서버를 만들지 않았음. 서울 열린데이터(http 전용) 등이 필요해지면 아래 원칙으로 만든다.
- **키를 저장하지 않는 순수 중계기**: 브라우저가 보낸 요청을 허용 목록에 있는 API 주소로만 전달하고 CORS 헤더를 붙여 돌려줌
- 허용 출처를 내 GitHub Pages 주소로 제한하고, 허용 API 주소를 화이트리스트로 관리 (남이 내 중계기를 쓰지 못하게)
- 무료 요금제 한도(하루 10만 요청)는 1인 사용에 충분
- 코드는 같은 저장소의 `relay/` 폴더에서 관리

### 2.2 기술 스택 (제안)

| 영역 | 선택 | 이유 |
|---|---|---|
| 빌드 | Vite + TypeScript | 빠른 개발, 타입으로 데이터 구조 오류 방지 |
| UI | React | 카드·편집·화면 전환이 많은 앱에 적합 |
| 지도 | OpenLayers + proj4 | 한국 좌표계(EPSG:5186·5179 등) 변환과 브이월드 WMTS 지원 |
| 공간 계산 | Turf.js | 반경·거리·면적·버퍼 |
| 일조 | SunCalc | API 없이 태양 고도·방위·일출일몰 계산 |
| 저장 | IndexedDB (Dexie) | 사진 같은 큰 파일도 브라우저에 저장 |
| 사진 메타데이터 | exifr | 사진의 촬영 위치·시간 자동 읽기 |
| 내보내기 | JSZip | 프로젝트 + 사진을 하나의 파일로 |
| 보고서 | 인쇄용 CSS → 브라우저 "PDF로 저장" | 별도 PDF 엔진 없이 한글 폰트 문제 회피 |
| 테스트 | Vitest | 챗봇 답변 파서 등 핵심 로직 검증 |
| 배포 | GitHub Actions → GitHub Pages | 커밋하면 자동 배포 |
| 중계 | Cloudflare Workers (wrangler) | 무료, 설정 간단 |

### 2.3 저장소 폴더 구조 (예정)

```text
/
├─ src/                 프론트엔드 앱
│  ├─ sources/          데이터 소스 플러그인 (브이월드, SGIS, 건축물대장 …)
│  ├─ prompts/          챗봇 프롬프트 템플릿 (요청서 9·10장 규칙 반영)
│  ├─ parser/           챗봇 답변 → 카드 변환
│  └─ ...
├─ relay/               Cloudflare Worker 중계 서버
├─ docs/                계획서, 데이터 카탈로그, 프롬프트 설계 문서
└─ .github/workflows/   자동 배포
```

## 3. 핵심 데이터 모델

요청서 5장(정보 유형)과 8.4·8.5장(데이터 구조)을 그대로 따릅니다.

### 3.1 프로젝트 (Project)
- 대지: 주소, PNU(필지 고유번호), 좌표, 대지 경계(GeoJSON), 조사 반경
- 과제 맥락 (F-02, 6.1): 프로젝트명, 건축 프로그램, 과제/공모전 주제, 규모, 대상자, 관심 관점, 피하고 싶은 일반적 해석, 답사 여부, 제출 결과물 형태
- **첫 질문** (6.2): "이 대지를 통해 가장 궁금한 것은 무엇인가?" + 선택지

### 3.2 출처 기록 (SourceRecord) — 요청서 8.4
`source_id, source_name, dataset_name, retrieved_at, update_date, geometry, coordinate_system, spatial_scale, time_range, raw_value, normalized_value, unit, license, limitations` + `original_url, reliability_tag`

- 원본(raw)과 가공값(normalized)을 분리 저장
- 데이터가 없으면 "없음"으로 기록하고 **임의 보정하지 않음**
- 데이터끼리 충돌하면 충돌 사실을 기록

### 3.3 카드 (Card) — 모든 사고 단위
- `type`: FACT / OBSERVATION / INTERPRETATION / TENSION / OPPORTUNITY / QUESTION / HYPOTHESIS / UNKNOWN
- `text`, `related_source_ids`, `related_card_ids`
- `origin`: 데이터 자동 생성 / 사용자 입력 / 챗봇 답변
- `confidence`, `human_validation_required`
- `user_status` (F-12): 동의 · 부분 동의 · 현장과 다름 · 중요하지 않음 · 더 조사하기 · 반대 해석 만들기 · 직접 수정 · 이 가설 발전시키기
- `history`: 수정 이력 (해석 변화 추적의 기반)

### 3.4 현장 관찰 (Observation)
사진, 위치(지도 지정 또는 사진 GPS 자동), 시간, 관찰 문장, 감각 키워드, 이용자·행위 태그, 개인적 느낌

### 3.5 설계 가설 (Hypothesis) — 요청서 F-11·9.4
제목, 근거 사실(카드 ID), 해석의 핵심, 해결하려는 긴장, 공간적 행동, 예상 사용자 경험, 장점, 위험·부작용, 추가 조사

### 3.6 챗봇 세션 (ChatSession)
생성한 프롬프트, 붙여넣은 답변 원문, 파싱 결과, 날짜, 사용한 챗봇 이름(사용자 입력)

## 4. 챗봇 왕복 설계 (이 프로그램의 핵심)

### 4.1 단계별 프롬프트
한 번에 모든 것을 요청하면 답이 얕아지므로, 요청서 9.1의 응답 순서를 여러 단계로 나눕니다.

| 단계 | 챗봇에게 요청하는 것 | 앱이 받아서 만드는 카드 |
|---|---|---|
| P1 관계 | 사실·관찰 사이의 관계 (F-08의 10가지 관계 유형) | INTERPRETATION(관계) |
| P2 긴장·기회 | 관계에서 생기는 갈등과 가능성 | TENSION / OPPORTUNITY |
| P3 복수 해석 | 핵심 현상마다 현실적·관계적·반전적 해석 3개 (F-09, 10.1 반전 질문) | INTERPRETATION ×3 |
| P4 설계 질문 | 보존·드러냄·연결·분리·공유·비움·변화 질문 (F-10) | QUESTION |
| P5 설계 가설 | 서로 다른 가설 3개 이상, 9.4 형식 (F-11, 10.2 공간 동사) | HYPOTHESIS |
| P6 심화 | 사용자가 고른·반박한 가설을 발전 또는 반대 해석 생성 | HYPOTHESIS / INTERPRETATION |
| P7 추가 조사·요약 | 추가 현장조사 질문, 패널용 요약문 | UNKNOWN / 요약문 |

### 4.2 모든 프롬프트에 들어가는 내용
- 역할과 원칙: 요청서 2.2(개발 방향), 9.2(금지 규칙), 9.3(권장 문체)을 지시문으로 포함
- 프로젝트 맥락: 과제·프로그램·관심 관점·첫 질문 답·피하고 싶은 해석
- **ID가 붙은 재료**: `F-01 …` (사실, 출처 포함), `O-01 …` (현장 관찰)
- 규칙: "제공된 F-/O- 번호만 근거로 인용할 것, 없는 수치를 만들지 말 것"
- **정해진 답변 형식** (앱이 다시 읽을 수 있도록), 예:

```text
### [INTERPRETATION] I-1
근거: F-03, O-02
내용: 거주인구는 감소하지만 특정 시간대 활동인구는 유지되고 있을 가능성이 있다.
확신도: 중간
확인 필요: 저녁 시간대 현장 관찰
```

### 4.3 답변 붙여넣기 → 카드
- 형식에 맞는 블록을 찾아 카드로 변환
- 존재하지 않는 F-/O- 번호를 인용하면 **"근거 확인 필요"** 표시
- 형식이 깨진 부분은 버리지 않고 "분류되지 않은 답변"으로 보여주고, 사용자가 직접 카드로 나눌 수 있게 함

### 4.4 길이와 사진
- 프롬프트 글자 수 표시. 길면 「1/3, 2/3, 3/3」으로 나눠 복사 (앞 조각에는 "아직 답하지 말고 '받음'이라고만 답하라" 지시)
- 사진은 텍스트로 붙여넣을 수 없으므로, 프롬프트에는 사진 번호와 설명만 넣고 **사진 묶음 다운로드** 후 챗봇에 직접 첨부하도록 안내

## 5. 데이터 카탈로그 (단계별 확장)

"최대한 다양한 자료" 요구에 맞춰 데이터 소스를 계속 추가할 수 있는 구조로 만들고, 아래 순서로 늘려갑니다. ✅는 이번 검증에서 호출 방식을 확인한 것, 🔍는 구현 시 확인할 것입니다.

| 단계 | 분류 | 데이터 | 출처 | 호출 | 확인 |
|---|---|---|---|---|---|
| A | 지도 | 기본지도·위성·하이브리드 | 브이월드 WMTS | 직접 | ✅ |

### Phase 0 — 기반 구축 ✅ 완료 (2026-11-08)

- 실제 키로 JSONP·CORS 재검증, 로컬 개발 방식 확정 (§8 참고)
- **완료 기준**: 배포 주소에서 브이월드 지도가 보이고 주소 검색이 된다

**결과**
- 저장소 `CJG10040/site-agent`, `main`에 올리면 GitHub Actions가 빌드 후 Pages에 자동 배포
- 구현: 브이월드 배경지도(일반·항공사진·회색·야간), 도로명·지번·장소 동시 검색, 지도 클릭 시 주소·필지(경계·PNU·공시지가)·용도지역 조회, 설정(키 브라우저 저장), 연결 진단 탭

### Phase 1 — 대지 입력과 지도 (화면 1·2, 데이터 단계 A) ✅ 개발 완료 (2026-11-09)

- 버스정류소는 TAGO가 주는 범위(대지 중심 주변 약 500m)만, 노선은 가까운 정류소 10곳까지만 조회
- 리포트의 분석 지도 4종에는 새 덧그림(재해·상가 등)을 넣지 않음

### Phase 7 — 선택 기능 (요청서 7.2 SHOULD)
- 과거 항공사진 비교, 관계선 직접 그리기, 두 대지 비교, 조사 버전 저장·해석 변화 추적, 교수 피드백 기록, 음성 메모(브라우저 음성인식)

### Phase 8 — 확장 검토 (필요 시)
- 다른 학생과 공유, 클라우드 저장, 공동 편집 → 이때 로그인·DB 도입을 다시 결정

## 8. 위험 요소와 확인할 사항

| 항목 | 내용 | 대응 |
|---|---|---|
| 실제 키 검증 | 이번 테스트는 무효 키 기준 | ✅ Phase 0에서 배포 주소 기준 정상 확인 |
| 로컬 개발 | 브이월드 키가 github.io로 등록되면 내 PC(localhost)에서는 안 될 수 있음 | 개발용 키 추가 발급 가능 여부 확인, 안 되면 배포 주소에서 바로 테스트 |
| 서비스 URL 형식 | 브이월드에 도메인만 등록하는지, 저장소 경로까지 넣는지 | Phase 0에서 확인 |
| 행정구역 코드 | 전북특별자치도 출범(2024)으로 시도 코드가 바뀌었고, **광주·전남 통합(전남광주통합특별시)이 브이월드 자료에 반영됨을 확인** (PNU 신 코드, 건물관리번호 구 코드 혼재) | Phase 2에서 SGIS·건축물대장 연동 시 신·구 코드 대응표 작성, 불일치 시 화면에 표시 |
| 패키지 공급망 | 공개 직후의 npm 패키지는 검증이 덜 되었을 수 있음 (suncalc 2.1.3이 당일 공개판이었고 각도 단위가 달라 오류 발생) | 공개 2주 이상 지난 판으로 고정해 설치 |
| 브라우저 저장 한계 | 사진 용량 제한, 브라우저 데이터 삭제 시 소실 | 정기적인 프로젝트 파일 내보내기 알림 |
| 공개 저장소 | 코드는 누구나 볼 수 있음 | 키·프로젝트 데이터는 저장소에 올라가지 않는 구조 |
| 챗봇 답변 형식 | 챗봇이 형식을 어길 수 있음 | 관대한 파서 + 수동 분류 기능 |
| 소지역 통계 | 개인정보 보호로 일부 값이 가려짐 | "데이터 없음"으로 표시, 보정하지 않음 |
| 이용 조건 | API별 이용약관·출처 표기 의무 | 출처 패널에 라이선스 표기 |
| API 변경 | 공공 API 주소·형식 변경 | 데이터 소스를 플러그인으로 분리해 개별 수정, 오류 시 사용자에게 설명 (숨기지 않음) |
