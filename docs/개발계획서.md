## 1. 사전 기술 검증 결과 (2026-11-08)

로컬에서 브이월드가 연결되지 않았던 원인은 **브이월드 API가 CORS 헤더를 보내지 않아 브라우저가 응답을 차단**하기 때문일 가능성이 큽니다. 브이월드는 `callback=` 파라미터를 주면 JSONP로 응답하므로, 정적 사이트에서도 일부 API는 직접 호출할 수 있습니다.

| 데이터 | 브라우저 직접 호출 | 방식 | 비고 |
|---|---|---|---|
| 브이월드 2D 데이터 API (`/req/data`) | ⭕ | JSONP | CORS 없음, JSONP 응답 확인 |
| 브이월드 검색 (`/req/search`)·주소 (`/req/address`) | ⭕ | JSONP | 위와 동일 서버 |
| 브이월드 지도 타일 (WMTS) | ⭕ | 이미지 | CORS 불필요 |
| 브이월드 부동산 속성 API (NED: 토지이용계획·공시지가 등) | ⭕ (2026-11-09 정정) | JSONP | 무효 키일 때만 JSONP가 아닌 오류를 돌려줘 막힌 것처럼 보였음. 유효한 키로는 JSONP 정상 |
| 브이월드 WFS | ❌ | 중계 필요 | CORS 없음 |
| SGIS (통계청 인구·가구·사업체) | ⭕ | fetch | `Access-Control-Allow-Origin: *` |
| 공공데이터포털 (`apis.data.go.kr`: 건축물대장·기상청 등) | ⭕ | fetch | 요청 출처를 허용하는 CORS 헤더 확인 |
| 카카오 로컬 (주변 시설) | ⭕ | fetch | CORS 허용 |
| 서울 열린데이터 | ❌ | 중계 필요 | http 전용 → https 사이트에서 차단 (현재 우선순위 낮음) |

> ⚠️ 위 표는 **유효하지 않은 테스트 키**로 응답 헤더만 확인한 결과입니다.
>
> ✅ **2026-11-08 실제 키 검증 (Phase 0):** 배포 주소(https://cjg10040.github.io/site-agent/)에서 브이월드 지도 타일·장소 검색·주소→좌표·2D 데이터(연속지적도) 네 항목이 모두 정상 응답. 정적 사이트 + JSONP 구조로 브이월드 직접 호출이 가능함을 확인.

## 2. 시스템 구성

```text
┌─────────────────────────── 사용자 브라우저 ───────────────────────────┐
│  GitHub Pages 정적 앱  (https://<계정명>.github.io/<저장소명>/)          │
│                                                                        │
│   설정 화면 ── API 키 입력 → 브라우저에만 저장(localStorage)             │
│   프로젝트 ── IndexedDB (대지·카드·사진) ⇄ 프로젝트 파일(.zip) 내보내기  │
│                                                                        │
│   ├─ 직접 호출 ──▶ 브이월드(JSONP·타일) / SGIS / 공공데이터포털 / 카카오  │
│   └─ 중계 호출 ──▶ Cloudflare Worker ──▶ 브이월드 NED·WFS 등            │
│                                                                        │
│   프롬프트 생성 ──(복사)──▶  [외부 챗봇: ChatGPT·Claude·Gemini 등]       │
│   카드 보드 ◀──(답변 붙여넣기 → 파서)──┘                                 │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.1 중계 서버(Cloudflare Worker) 원칙 — 현재 불필요 (참고용으로 남김)

- 2026-11-09 기준 사용하는 API(브이월드 전체, SGIS, 건축HUB)가 모두 브라우저에서 직접 호출되어 중계 서버를 만들지 않았음. 서울 열린데이터(http 전용) 등이 필요해지면 아래 원칙으로 만든다.
- **키를 저장하지 않는 순수 중계기**: 브라우저가 보낸 요청을 허용 목록에 있는 API 주소로만 전달하고 CORS 헤더를 붙여 돌려줌
- 허용 출처를 내 GitHub Pages 주소로 제한하고, 허용 API 주소를 화이트리스트로 관리 (남이 내 중계기를 쓰지 못하게)
- 무료 요금제 한도(하루 10만 요청)는 1인 사용에 충분
- 코드는 같은 저장소의 `relay/` 폴더에서 관리

### 2.2 기술 스택 (제안)

| 영역 | 선택 | 이유 |
|---|---|---|
| 빌드 | Vite + TypeScript | 빠른 개발, 타입으로 데이터 구조 오류 방지 |
| UI | React | 카드·편집·화면 전환이 많은 앱에 적합 |
| 지도 | OpenLayers + proj4 | 한국 좌표계(EPSG:5186·5179 등) 변환과 브이월드 WMTS 지원 |
| 공간 계산 | Turf.js | 반경·거리·면적·버퍼 |
| 일조 | SunCalc | API 없이 태양 고도·방위·일출일몰 계산 |
| 저장 | IndexedDB (Dexie) | 사진 같은 큰 파일도 브라우저에 저장 |
| 사진 메타데이터 | exifr | 사진의 촬영 위치·시간 자동 읽기 |
| 내보내기 | JSZip | 프로젝트 + 사진을 하나의 파일로 |
| 보고서 | 인쇄용 CSS → 브라우저 "PDF로 저장" | 별도 PDF 엔진 없이 한글 폰트 문제 회피 |
| 테스트 | Vitest | 챗봇 답변 파서 등 핵심 로직 검증 |
| 배포 | GitHub Actions → GitHub Pages | 커밋하면 자동 배포 |
| 중계 | Cloudflare Workers (wrangler) | 무료, 설정 간단 |

## 3. 핵심 데이터 모델

요청서 5장(정보 유형)과 8.4·8.5장(데이터 구조)을 그대로 따릅니다.

### 3.1 프로젝트 (Project)
- 대지: 주소, PNU(필지 고유번호), 좌표, 대지 경계(GeoJSON), 조사 반경
- 과제 맥락 (F-02, 6.1): 프로젝트명, 건축 프로그램, 과제/공모전 주제, 규모, 대상자, 관심 관점, 피하고 싶은 일반적 해석, 답사 여부, 제출 결과물 형태
- **첫 질문** (6.2): "이 대지를 통해 가장 궁금한 것은 무엇인가?" + 선택지

### 3.2 출처 기록 (SourceRecord) — 요청서 8.4
`source_id, source_name, dataset_name, retrieved_at, update_date, geometry, coordinate_system, spatial_scale, time_range, raw_value, normalized_value, unit, license, limitations` + `original_url, reliability_tag`

- 원본(raw)과 가공값(normalized)을 분리 저장
- 데이터가 없으면 "없음"으로 기록하고 **임의 보정하지 않음**
- 데이터끼리 충돌하면 충돌 사실을 기록

### 3.3 카드 (Card) — 모든 사고 단위
- `type`: FACT / OBSERVATION / INTERPRETATION / TENSION / OPPORTUNITY / QUESTION / HYPOTHESIS / UNKNOWN
- `text`, `related_source_ids`, `related_card_ids`
- `origin`: 데이터 자동 생성 / 사용자 입력 / 챗봇 답변
- `confidence`, `human_validation_required`
- `user_status` (F-12): 동의 · 부분 동의 · 현장과 다름 · 중요하지 않음 · 더 조사하기 · 반대 해석 만들기 · 직접 수정 · 이 가설 발전시키기
- `history`: 수정 이력 (해석 변화 추적의 기반)

### 3.4 현장 관찰 (Observation)
사진, 위치(지도 지정 또는 사진 GPS 자동), 시간, 관찰 문장, 감각 키워드, 이용자·행위 태그, 개인적 느낌

### 3.5 설계 가설 (Hypothesis) — 요청서 F-11·9.4
제목, 근거 사실(카드 ID), 해석의 핵심, 해결하려는 긴장, 공간적 행동, 예상 사용자 경험, 장점, 위험·부작용, 추가 조사

### 3.6 챗봇 세션 (ChatSession)
생성한 프롬프트, 붙여넣은 답변 원문, 파싱 결과, 날짜, 사용한 챗봇 이름(사용자 입력)

## 4. 챗봇 왕복 설계 (이 프로그램의 핵심)

### 4.1 단계별 프롬프트
한 번에 모든 것을 요청하면 답이 얕아지므로, 요청서 9.1의 응답 순서를 여러 단계로 나눕니다.

| 단계 | 챗봇에게 요청하는 것 | 앱이 받아서 만드는 카드 |
|---|---|---|
| P1 관계 | 사실·관찰 사이의 관계 (F-08의 10가지 관계 유형) | INTERPRETATION(관계) |
| P2 긴장·기회 | 관계에서 생기는 갈등과 가능성 | TENSION / OPPORTUNITY |
| P3 복수 해석 | 핵심 현상마다 현실적·관계적·반전적 해석 3개 (F-09, 10.1 반전 질문) | INTERPRETATION ×3 |
| P4 설계 질문 | 보존·드러냄·연결·분리·공유·비움·변화 질문 (F-10) | QUESTION |
| P5 설계 가설 | 서로 다른 가설 3개 이상, 9.4 형식 (F-11, 10.2 공간 동사) | HYPOTHESIS |
| P6 심화 | 사용자가 고른·반박한 가설을 발전 또는 반대 해석 생성 | HYPOTHESIS / INTERPRETATION |
| P7 추가 조사·요약 | 추가 현장조사 질문, 패널용 요약문 | UNKNOWN / 요약문 |

### 4.2 모든 프롬프트에 들어가는 내용
- 역할과 원칙: 요청서 2.2(개발 방향), 9.2(금지 규칙), 9.3(권장 문체)을 지시문으로 포함
- 프로젝트 맥락: 과제·프로그램·관심 관점·첫 질문 답·피하고 싶은 해석
- **ID가 붙은 재료**: `F-01 …` (사실, 출처 포함), `O-01 …` (현장 관찰)
- 규칙: "제공된 F-/O- 번호만 근거로 인용할 것, 없는 수치를 만들지 말 것"
- **정해진 답변 형식** (앱이 다시 읽을 수 있도록), 예:

```text
### [INTERPRETATION] I-1
근거: F-03, O-02
내용: 거주인구는 감소하지만 특정 시간대 활동인구는 유지되고 있을 가능성이 있다.
확신도: 중간
확인 필요: 저녁 시간대 현장 관찰
```

### 4.3 답변 붙여넣기 → 카드
- 형식에 맞는 블록을 찾아 카드로 변환
- 존재하지 않는 F-/O- 번호를 인용하면 **"근거 확인 필요"** 표시
- 형식이 깨진 부분은 버리지 않고 "분류되지 않은 답변"으로 보여주고, 사용자가 직접 카드로 나눌 수 있게 함

### 4.4 길이와 사진
- 프롬프트 글자 수 표시. 길면 「1/3, 2/3, 3/3」으로 나눠 복사 (앞 조각에는 "아직 답하지 말고 '받음'이라고만 답하라" 지시)
- 사진은 텍스트로 붙여넣을 수 없으므로, 프롬프트에는 사진 번호와 설명만 넣고 **사진 묶음 다운로드** 후 챗봇에 직접 첨부하도록 안내

## 6. 개발 단계 (로드맵)

각 단계가 끝나면 **실제 대지 1곳(광주·전남·전북)** 으로 직접 써보고, 피드백을 반영한 뒤 다음 단계로 넘어갑니다.

### Phase 0 — 기반 구축 ✅ 완료 (2026-11-08)
- Git 설치, GitHub 저장소 생성, 자동 배포 설정
- 브이월드 서비스 URL을 Pages 주소로 수정
- 실제 키로 JSONP·CORS 재검증, 로컬 개발 방식 확정 (§8 참고)
- **완료 기준**: 배포 주소에서 브이월드 지도가 보이고 주소 검색이 된다

**결과**
- 저장소 `CJG10040/site-agent`, `main`에 올리면 GitHub Actions가 빌드 후 Pages에 자동 배포
- 구현: 브이월드 배경지도(일반·항공사진·회색·야간), 도로명·지번·장소 동시 검색, 지도 클릭 시 주소·필지(경계·PNU·공시지가)·용도지역 조회, 설정(키 브라우저 저장), 연결 진단 탭
- 실제 키로 연결 진단 4개 항목 모두 정상 (배포 주소 기준)
- 남은 확인: 내 PC(localhost)에서 같은 키가 동작하는지 → 동작하지 않으면 개발 중 확인은 배포 주소에서 진행
- 용도지역 레이어의 이름 필드(`uname` 등)는 Phase 1에서 실제 응답을 보고 확정

### Phase 1 — 대지 입력과 지도 (화면 1·2, 데이터 단계 A) ✅ 개발 완료 (2026-11-09)
- 새 프로젝트: 과제 맥락 입력 + **첫 질문**을 데이터 수집보다 먼저 묻기
- 대지 지정: 주소 검색 / 지도 클릭 / 좌표 입력 → 필지 선택 → 경계 수정·그리기, 조사 반경 설정
- 레이어: 기본지도·항공사진·지적·용도지역·건물·도로·행정경계, 태양 궤적
- 수집한 데이터 → 출처 기록 + **FACT 카드 초안**(사용자가 확인해야 FACT로 확정)
- 설정 화면(API 키), 브라우저 저장, 프로젝트 파일 내보내기/가져오기
- **완료 기준**: 실제 대지에 대해 출처가 붙은 FACT 5개 이상

**인터뷰로 정한 것 (2026-11-09)**: 단계형 화면 + 자유 이동 / 필지 여러 개 선택 + 직접 그리기 / 예시 대지(광주 충장로)로 개발 검증 / 레이어는 앱 안 브라우저에서 실제 키로 확인

**결과**
- 화면 흐름: ① 과제 ② 첫 질문 ③ 대지 ④ 공간정보 ⑤ 사실 카드 (⑥~⑧은 '준비 중'으로 표시), 단계 옆에 진행 상태
- 대지: 필지 클릭으로 넣기/빼기, 다각형 직접 그리기 → 걸친 필지 자동 조회, 꼭짓점 수정, 반경 250m·500m·1km, 좌표 입력
- 공간정보: 24개 레이어 수집 → 출처 기록(S-번호), 원자료 보관, 지도 표시(건물 층수별 색, 도로망, 태양 궤적, 브이월드 주제도)
- 사실 카드: 위치·필지·면적·용도지역·용도지구·보호구역·공시지가·주변 건물(층수·용도·노후도)·도로 접면·도시계획시설·일조 → FACT 초안, 확인 불가 항목은 UNKNOWN
- 다시 수집해도 사용자가 확인·수정한 카드와 그 출처는 유지 (손대지 않은 초안만 갱신)

### Phase 3 — 현장 관찰 입력 (화면 4) ✅ 개발 완료 (2026-11-09)

- **완료 기준**: OBSERVATION 5개 이상, 지도에 표시

**인터뷰로 정한 것 (2026-11-09)**: 현장(휴대폰)과 PC 둘 다 사용 → 기기 간 관찰 합치기 / 관찰 1개에 사진 여러 장 / 사진은 줄여서 저장 / 관찰마다 사실을 연결해 비교

**결과**
- 관찰은 O-번호 카드(사실 F-번호와 같은 체계)로 저장 → Phase 4 프롬프트에서 근거 번호로 사용
- 관찰 입력: 사진 여러 장(촬영·앨범), 관찰 문장(+음성 입력), 위치(사진 정보·현재 위치·지도에서 지정 → "대지 북동쪽 300m"처럼 표시), 시간(사진 촬영 시각·지금·직접 입력 → 오전/오후/저녁/밤/새벽·평일/주말), 감각·이용자·행위 태그(기본 목록 + 직접 입력), 느낌, 날씨·상황, '새로운 발견' 표시
- 사진: 사진 정보(EXIF)에서 위치·시간을 먼저 읽고 긴 변 2048px JPEG(장당 수백 KB)로 줄여 브라우저 저장소(IndexedDB, 프로젝트와 별도 표)에 저장, 회전 방향 반영
- 비교: 관찰마다 관련 사실을 골라 '일치 / 현장과 다름' 표시 → '자료와 비교' 보기에 다름·새 발견·일치를 모아 보여 줌, 사실 카드에도 "현장 관찰: O-01 다름" 표시
- 지도: 관찰 번호 표시(검정 관찰, 빨강 자료와 다름, 청록 새 발견), 누르면 그 관찰 열기
- 기기 간 이동: 내보내기 파일에 사진 포함(base64), 사본 가져오기 시 사진 번호 새로 발급, **다른 기기의 관찰 합치기**(같은 관찰은 더 최근 수정본으로, 새 관찰은 새 번호로, 다른 프로젝트에서 온 관찰의 사실 연결은 지우고 알림)
- 시간대 필터, 단계 표시("관찰 n개 · 다름 m")
- 검증: 시험 이미지로 사진 처리·저장(2048px), 태그·시간대, 지도 지정, 사실 연결·비교 보기, 지도 표시 클릭, 내보내기→합치기(같은 프로젝트/다른 프로젝트), 휴대폰 폭 화면 확인

**남은 것 / 확인 못 한 것**
- 실제 휴대폰 사진의 위치 정보 읽기: 시험 이미지에는 위치 정보가 없어 미검증. 휴대폰 브라우저는 업로드 시 위치를 지우는 경우가 많아 '현재 위치' 버튼을 함께 둠

- 연결 진단: 새 항목 2개(ASOS 시간자료, 국가교통정보센터) 포함 전부 정상

- 개방감: 건물·지형 높이 칸에서 16방위로 300m까지 가장 높은 올려본각 → 하늘 보이는 비율(SVF). 건물 안 칸은 제외. 대지 하늘 그림은 대지 가운데 눈높이 1.5m에서 360방위(건물 도형과 직접 교차) + 동지·춘추분·하지 태양 궤적 겹침
- 가시권: 바깥 칸(눈높이 1.5m)에서 대지 중심을 향해 걸어가며 가장 큰 가림 각을 찾아 **'이 칸에서 보이려면 대지에 몇 m 이상 지어야 하는지'**를 칸마다 한 번 계산·저장 → 고정 높이·내 높이는 다시 계산 없이 바로 나눔
- 수목: 브이월드 위성영상(줌 17~18) 타일 → 초록 지수(2G−R−B)·밝기 기준으로 나무 그늘 칸(2m), 건물 발자국 제외. 그림자 속 나무·잔디 혼동은 한계로 표기
- 바람 흐름(실험): 대지 중심 약 600m 정사각 영역을 바람 방향에 맞춰 돌려 4m 칸 D2Q9 격자 볼츠만, 건물 = 막힌 칸. 결과는 들어오는 바람 대비 속도 비(가속·정체 구역). 실제 풍속·난류 아님 표기
- 열쾌적(실험): 기온·습도(ASOS 더운 오후) + 바람(관측 풍속 × 여름 바람 실험 속도 비) + 평균복사온도(햇빛 여부·개방감·나무 그늘로 단순 계산) → UTCI(공식 다항식, MIT 공개 코드 jsthermalcomfort에서 함수만 옮겨 출처 표기). 열 스트레스 단계로 칠함
- 저장: 칸 자료는 압축(fflate)해 프로젝트에 저장. 반경 1km에서도 합계 1~2MB 목표
- 새 도판(9장): 일조시간(대지 주변·반경 전체), 개방감 지도, 대지 하늘 그림, 높이별 가시권, 수목, 바람 흐름(여름·겨울), 여름 열쾌적 → 모두 '계산값·참고용', 실험 2종은 '실험' 표시
- 새 사실 카드: 대지 일조(동지 평균·연속 2시간 확보 비율), 대지 개방감, 가시권 면적(높이별), 수목 비율, 바람 실험(대지 주변 가속·정체), 열쾌적 실험(대지 주변 UTCI 범위) — 계산값은 confidence 'medium', 실험은 'low' + 확인 필요
- 사용자 준비물: 없음 (이미 있는 키·자료로 계산)

**결과 (2026-11-11, 배포 사이트, 금남로 옆 시험 대지, 반경 500m, 건물 3,015동)**
- 계산 시간 약 17초: 일조 반경 1.8초·대지 주변 0.8초, 개방감 0.3초, 가시권 0.03초, 수목 0.2초(위성영상 25장), 바람 실험 2방향 13.8초. 저장 약 0.43MB
- 사실 카드: 대지 안 동지 평균 2.6시간(09~15시 연속 2시간 50%, 08~16시 4시간 34%), 대지 개방감 70%(남동쪽 75°까지 가림), 가시권 10m 2%·80m 21%, 초록 덮개 29%, 바람 실험 대지 주변 여름 0.46배·겨울 0.58배, 더운 여름 오후(34.5℃·54%) 대지 주변 UTCI 35.5~43℃
- 확인한 것: UTCI 함수가 원본 예시(25℃·25℃·1m/s·50% → 24.6)와 같음. 위성영상 초록은 금남로 가로수·문화전당 녹지를 잘 잡음
- 고친 것
  - 바람 실험이 처음엔 영역의 92%가 '거의 멈춤' — 평면 계산에서 낮은 건물이 빽빽한 동네가 통째로 벽이 되기 때문. **높이 20m(약 7층) 이상만 막고, 낮은 건물은 높이에 비례해 바람을 줄이며 지나가게**(다공성 칸) 바꾸고 이완 시간 0.6으로 안정화 → 바람 방향과 나란한 길이 빨라지고 가로지르는 길이 느려지는 모양이 나옴
  - 금남지하상가·문화전당역처럼 **지하만 있는 시설**(지상층 없음 + 지하층 있음 + 건축면적 0)이 3m 건물로 계산되던 것 → 계산에서 뺌
  - 하늘 그림 범례 글자가 잘리던 것
- 한계: 층수 모르는 건물 약 25%(대부분 작은 부속 건물)는 3m로 봄 / 반경 밖 건물 그림자는 빠짐 / 바람 실험은 영역이 최대 800m 정사각

### 상가·생활 시설 도판 디벨롭 (2026-11-11, 사용자 검토) — 도판 41장
**인터뷰로 정한 것**: 상가는 지금 '건물별 업종 색'에 더해 **낮·밤 성격**과 **대지 주변 vs 동네 비교** / 생활 시설은 **지도(아이콘 + 걸어서 몇 분) + 생활권 다이어그램** / 분류는 **생활 영역 6묶음**(교통·교육·의료·장보기·문화·공공)

- **상가 낮·밤 성격** (지도): 업종(대·중·소분류)으로 낮(소매·학원·병원·사무 등)·종일(음식·카페·편의점)·밤(주점·유원지·오락·숙박)을 나누고, 건물마다 절반 넘는 쪽으로 칠함(없으면 '섞임'). 실제 영업시간이 아님을 표기
- **대지 주변 vs 동네 업종** (막대 그림, 지도 틀 없음): 중분류별로 대지 경계 100m 안 비율과 반경 전체 비율을 나란히. 대지 주변에 3곳 이상이면서 1.5배 넘게 많으면 '×n 많음', 동네에 3% 넘게 흔한데 대지 주변에 없으면 '대지 주변엔 없음'
- **생활 시설 (걸어서 가장 가까운 곳)** (지도): 12분류 아이콘(앱에서 그린 단순 기호: 열차·P·깃발·집·책·십자·캡슐·카트·24·별·사진기·기둥 건물)을 6묶음 색으로. 분류마다 가장 가까운 곳은 진한 아이콘 + 대지에서 점선 + '걸어서 n분'(길의 연결이 있으면 도로중심선 따라, 없으면 직선 × 1.3). 도판 밖이면 가장자리에 '(도판 밖)'. 라벨은 겹치지 않게 위아래로 비켜 놓음
- **생활권 (걸어서 5·10·15분 안)** (다이어그램, 지도 틀 없음): 분류마다 5·10·15분 안 시설 수를 점으로(7곳 넘으면 +수, 카카오가 15곳까지만 줘서 '15+'), 오른쪽에 가장 가까운 곳 분
- 사실 카드 2장: `stores-time`(반경 vs 대지 100m 안 낮·종일·밤 비율), `stores-special`(대지 주변에 많은 업종 ×배, 없는 업종)
- 시험(충장로 금남로 옆): 대지 주변에 섬유·의복·신발 소매 49%(동네 24%, ×2) — 충장로 패션 거리와 일치 / 반경 안 밤 업종 8%, 대지 100m 안 4% / 지하철역 2분, 학교 6분, 대형마트 23분(도판 밖)

#### 종합 다이어그램
**인터뷰로 정한 것**: **카드에서 놓고 직접 그리기** / 기호 = **화살표·영역·포인트(점·별·번개)·글상자** / 바탕 = **회색 건물·도로, 도판을 골라 바꾸기** / **⑧ 해석·가설에서 그리고 ⑨ 리포트·보드에는 마지막 도판으로**

**만든 것**
- ⑧ 해석·가설에 '종합 다이어그램' 탭: 도구(고르기·옮기기, 화살표, 영역, 포인트, 글상자, 카드 놓기), 색 = 설계 방향(보존할 것·드러낼 것·피할 것·변환할 것·그 밖 — 긴장·기회 카드의 '방향'과 같음), 카드 목록에서 [놓기] → 지도 누르기(카드 번호 배지 + 제목, 색은 카드의 방향)
- 그리기: 화살표·영역은 차례로 누르고 두 번 누르기나 Enter로 마침(Esc 취소), 기호를 끌어 옮기기·꼭짓점 끌기, Delete로 지우기, 글상자 지시선 끝 찍기, 화살표 양쪽, 포인트 모양. 가는 선도 고르기 쉽게 편집 화면에만 보이지 않는 넓은 누를 자리
- 바탕: 회색 건물·도로(수치지도가 있으면 도로 면도) 또는 지도 도판 하나를 45%로 연하게(항공사진·지형·선택도 등), 도판 반경 150~수집 반경
- 완성 도판 'synth'(그룹 '종합', 마지막 번호): 범례 '색 = 설계 방향' + 기호 뜻, 요약(기호·카드 목록 — 챗봇 결론 프롬프트에도 들어감), 출처 '학생이 그린 해석이며 사실이 아님'. ⑥ 도판 목록·⑨ 리포트·보드에 자동으로, SVG·PNG
- 고친 것(로컬 시험): 그린 직후 다음 색을 고르면 방금 그린 기호 색까지 바뀌던 것 → 색 버튼은 '고르기' 도구일 때만 고른 기호를 바꿈 / 가는 화살표가 잘 안 골라지던 것 / 카드 글이 작고 옅던 것

#### 조사 버전 저장·비교
**인터뷰로 정한 것**: 이번엔 **조사 버전만** / 저장은 **직접 + 자동**(다시 수집 직전·리포트 인쇄 때)

**만든 것**
- 저장소: IndexedDB에 'versions' 칸을 새로(Dexie 3판) — 프로젝트는 고칠 때마다 저장되므로 그 안에 넣지 않음. 버전 = 이름·시각·저장 이유 + 해석 스냅숏(카드 전부, 도판 결론, 대지해석 요약문, 첫 질문, 과제, 종합 다이어그램, 대지 요약·수집 시각). 수집 원자료는 넣지 않음
- 저장: 위 막대 '버전 저장'(이름 칸, 예: 중간 크리틱 전) / 자동은 다시 수집 직전·리포트(보드) 인쇄 뒤, 바로 앞 버전과 해석이 같으면 건너뜀, 자동 버전은 최근 20개까지
- ⑨ 리포트 › '변화 기록': 버전 목록(이름 바꾸기·지우기, 종류별 카드 수), 두 시점 비교(이전 버전 → 다른 버전 또는 '지금') — 한 줄 요약, 종류별 카드 수 표(늘면 초록·줄면 빨강), 첫 질문, 카드(생김·빠짐·바뀜 — 바뀐 내용은 지운 글/새 글, 상태·반응·칸 변화), 도판 결론, 요약문, 종합 다이어그램 두 시점 그림 나란히
- 리포트 '해석 과정 기록'에 조사 버전 목록(이름·날짜·이유·카드 수)
- 프로젝트 파일 내보내기에 버전을 함께 넣고, 가져오면 버전도 돌아옴(사본으로 가져오면 새 프로젝트에). 프로젝트를 지우면 버전도 지움

#### 교수 피드백
**인터뷰로 정한 것**: 피드백마다 날짜·누가(교수·조교·동료)·내용·관련 카드·도판·반영 상태(반영함·보류·다르게 판단)·어떻게 반영했는지, 리포트에 넣기

**만든 것**
- ⑧ 해석·가설 '피드백' 탭: 받은 날·누가(교수·조교·동료·외부 전문가·기타)·자리(중간 크리틱 등)·내용, 관련 카드·도판 고르기, 번호 FB-01…, 자리(날짜)별로 묶어 보기, 고치기·지우기
- 반영 상태 아직 안 정함·반영함·보류·다르게 판단(색 띠) + 상태에 맞는 안내 문구로 '어떻게 반영했는지 / 왜 보류·다르게 판단했는지'
- 적을 때 **받은 시점의 해석을 조사 버전으로 저장**(기본 켜짐, 버전 이유 '피드백 받을 때') → 피드백마다 '받은 뒤 바뀐 것: 카드 1개 바뀜 …'(피드백 기록 자체는 빼고 해석의 변화만)
- 이어 보이는 곳: 카드 상세 '받은 피드백'(상태 표), ⑥ 도판 카드에 그 도판 피드백 줄, ⑨ 리포트 '받은 피드백과 반영' 표(번호·날짜·누가·자리·내용·관련 카드와 도판 번호·상태·반영), 변화 기록 비교에 '피드백 n개 적음·반영 상태 바뀜'
- 챗봇 프롬프트(챗봇 왕복·도판 결론)의 과제 맥락에 피드백과 학생의 판단 — '다르게 판단한 것은 그 판단을 존중'하라고 적음
- 함께 고친 것: 변화 요약이 '1개 바뀜'처럼 '카드' 없이 나오던 것

**로컬에서 확인**: 피드백 적기(카드 T-01·도판 '상가 낮·밤 성격' 연결) → 버전 '중간 크리틱 (날짜)' 자동 저장 → 반영함 + 반영 내용 → 카드 고친 뒤 '받은 뒤 바뀐 것: 카드 1개 바뀜' / 카드 상세·⑥ 도판 카드·리포트 표에 나옴 / 프롬프트 블록(Node)에 피드백·도판 제목·반영 내용

**로컬에서 확인 (조사 버전)**: 버전 저장 → 카드 추가·수정·제외·반응, 결론 2개, 첫 질문, 종합 기호 추가 → 비교가 '카드 1개 생김, 1개 빠짐, 2개 바뀜, 도판 결론 2개 바뀜, 종합 다이어그램 기호 +1, 첫 질문 바뀜'으로 맞게 나옴 / 인쇄 뒤 자동 저장 1개, 바뀐 것 없이 다시 인쇄하면 건너뜀 / 내보낸 파일에 버전 2개, 지우고 가져오면 버전 2개 복원

### 11.2 작성 원칙 (그대로 받아들일 것)
- 도판 한 장 = 사실 하나 (한 도판에 두 주제를 얹지 않음)
- 주제색 한 계열 + 회색 바탕, 강조색은 대지 표식 하나
- 모르는 값은 색을 지어내지 않고 회색 "미상"
- 모든 도판 같은 반경·축척, 북쪽 고정, 축척·방위 표기
- 자료 기준일·추정치(층수→높이 환산 등)·평활 등 한계를 캡션에 표기
- **도판마다 결론 한 문장**, 마지막에 **종합 다이어그램** — "판단 없는 사실 나열"이 가장 흔한 오류
- 반경 기준: 150~300m 인접 관계, 500m 도보 5~7분(기본), 800m 생활권, 1km 넘으면 도시 구조
